# Ponytail audit — cmd-mod-better-sub-agents

**What this repo does:** A "Command Code" mod that lets an AI coding session hand off work to a background process and get the result back later as its own message. You call `subagent_spawn`, it returns in milliseconds, and the answer arrives as a separate message when the worker finishes. The two sides never block each other. There is no server: the handoff is a directory of JSON files on disk, which a worker writes into and the parent polls every 400ms.

**Load assumed:** one person in a terminal, with maybe 1-10 background workers running at once, and occasionally a second session open against the same spool. Not a server. Scale problems below are judged at that load — a few dozen files in the spool, not thousands.

---

## Must fix

### 1. A foreign backlog made every tick do unbounded work
`src/delivery.ts:192` (before `21eaa65`)

- **What this is:** The drain looks through the shared inbox folder for signals this session owns. Anything belonging to another session gets put back.
- **Problem:** The pass looked at *every* file in the folder, and the two counters (`FILES_PER_DRAIN_MAX`, `PENDING_SCAN_MAX`) only counted signals this session owned. A foreign signal was claimed, read and put back without counting, so the work scaled with the whole backlog while the counters stayed at zero. It also re-read the folder once per signal, so the pass was quadratic on top of that. With 100 foreign signals, one pass did 200 file renames — and it ran every 400ms and every status refresh. An offline session's leftovers could make the whole mod feel stuck.
- **Fix:** A pass now has a budget of files it may look at, the folder is read once per pass, and a cursor carries over so a bounded pass still works through a long backlog instead of re-reading the same head. **Fixed in `21eaa65`.**

### 2. One session's cleanup erased another session's delivery records
`src/ledger.ts:53` (before `eaa91f3`)

- **What this is:** A ledger file, `delivered.jsonl`, records which signals were already delivered, so a restart does not deliver the same result twice. Every session shares the one file.
- **Problem:** Each session kept its own in-memory list of what *it* had delivered. When a session's list grew past the cap, it compacted by rewriting the whole file from that private list — so another session's recent deliveries were erased from disk. After a restart, that other session delivered the same result a second time.
- **Fix:** The compaction now merges what the file actually holds before it prunes, so the file stays the truth. **Fixed in `eaa91f3`.**

### 3. A job that already failed could fail again
`src/state.ts:73` (before `eaa91f3`)

- **What this is:** A table of which job states may follow which.
- **Problem:** The table said a job may keep the state it already has. So a spawn that failed for one reason and then failed again — a spawn with no process id, then its late error event — wrote a second failure signal, and the second one overwrote the saved reason and the finish time. The first explanation of what went wrong was lost.
- **Fix:** A terminal state is terminal, even for itself. **Fixed in `eaa91f3`.**

### 4. A timed-out command left its children running
`src/index.ts:468` (before `68ea71a`)

- **What this is:** A command job runs under `/bin/sh -c` in a detached worker, and the job has a timeout.
- **Problem:** The timeout signalled the shell only. A command that backgrounds itself — `(sleep 30; …) &` — left that grandchild running after the job had already reported a timeout. The work carried on past the bound the caller set, with nobody watching it.
- **Fix:** A command now runs in its own process group, and the timeout signals the group. **Fixed in `68ea71a`.**

### 5. A follow-up lost the tool set the first run had
`src/plan.ts:544` (before `a62584a`)

- **What this is:** The job record saves what a run resolved, so a follow-up continues it exactly.
- **Problem:** The record saved the allowed-tools list but not the denied-tools list, so a follow-up restored the *definition's* deny list instead of the run's. A definition denying `Bash`, overridden at spawn with `disallowed_tools: Write`, could use `Bash` in the first run — its saved list includes it — and the follow-up then blocked `Bash`. The work could not continue.
- **Fix:** The resolved deny list is saved with the job and restored with the allowlist. **Fixed in `a62584a`.**

### 6. A run narrowed by the caller was never checked
`src/plan.ts:408` (before `a62584a`)

- **What this is:** A flag that tells the worker "your tool list must be enforced", and makes the worker refuse to run if the mod did not load in the agent's own session.
- **Problem:** The flag was worked out from the definition only. A run narrowed by the *caller's* `tools` argument was not flagged, so the worker ran with an allowlist it never enforced — the exact opposite of what the caller asked for.
- **Fix:** The record now carries the flag. **Fixed in `a62584a`.**

### 7. An agent with an empty body could not start
`src/index.ts:2738` (before `24e7a57`)

- **What this is:** A marker file that says "the mod loaded in the agent's own session".
- **Problem:** The marker was only written when the definition had a body. An agent with an empty body and no appended text had no marker, so the worker decided the mod had not loaded and stopped before the task — and the tool check was never in place.
- **Fix:** The marker is about the mod, not the body. **Fixed in `24e7a57`.**

### 8. A held signal could vanish
`src/delivery.ts:256` (before `5619c33`)

- **What this is:** When a drain finds a signal belonging to another session, it puts it back.
- **Problem:** If the put-back rename failed, the code wrote the signal straight to its visible name in the inbox. Another session's drain could claim that file while the write was still going, read half a JSON, treat it as broken and delete it — and the writer then deleted the claimed copy too. The result was gone, and nobody was told.
- **Fix:** The write goes to a name the inbox scan ignores and is renamed into place, so a reader only ever sees a whole signal. **Fixed in `5619c33`.**

### 9. A session's own result never arrived past a foreign backlog
`src/delivery.ts:217` (before `b409a85`)

- **What this is:** The pass has a budget of files it may look at, and a cursor that carries over between passes so a long backlog is worked through.
- **Problem:** The cursor advanced *before* the budget was checked, so the pass stepped over the first file it did not look at and the next pass started after it. That file was then skipped by every later pass. With a backlog of exactly one pass worth of foreign files and the session's own result right behind them, the result was never delivered at all — the session waited for an answer that could not arrive.
- **Fix:** The budget is checked before the cursor moves, so the pass stops on the first file it did not look at and the next pass starts there. **Fixed in `b409a85`.**

### 10. A command that exited at once did not stop its own work
`src/index.ts:502` (before `62055ff`)

- **What this is:** A command runs under `/bin/sh -c` in its own process group, and the job has a timeout.
- **Problem:** The group signal covered the case where the shell was still running when the timeout fired. But a command can exit *immediately* and leave a background child behind: `(sleep 30; do_work) &` makes the shell exit at once. The shell's exit reported success and cleared the pending SIGKILL, so the background work kept running with nobody stopping it — and the caller already had its result.
- **Fix:** The worker checks whether the group is still alive, signals it, waits for it to go, and escalates to SIGKILL if it does not. The result is only written once the group is gone. **Fixed in `62055ff`.**

### 11. The same result was delivered twice
`src/delivery.ts:249` (before `b1495a0`)

- **What this is:** The claim collects a batch of signals and hands them to the caller.
- **Problem:** The ledger guard is checked while the batch is being built, and nothing recorded a delivered id until the batch was handed over. Two files carrying the same signal id both passed the guard, so the batch held the same result twice and the continuation reason reported it twice. A failed spawn produces exactly that pair: the missing-pid branch emits one failure and the error handler emits another.
- **Fix:** A pass remembers the ids it has claimed. **Fixed in `b1495a0`.**

### 12. A duplicate file recorded the result as delivered before it was
`src/delivery.ts:260` (before `71fb86e`)

- **What this is:** The pending count walks the same files the drain does, and settles what it finds.
- **Problem:** The fix above settled a duplicate copy as *delivered*, which recorded the signal id in the ledger before the result had been delivered. The count held the first copy and settled the second as delivered, so the id was in the ledger while the real result was still waiting. The next drain saw the id, deleted the first copy as already delivered, and the conversation received neither copy. The result disappeared.
- **Fix:** A duplicate copy is *discarded*: the file is removed, but the id is not recorded as delivered, so the copy that is still waiting is delivered normally. **Fixed in `71fb86e`.**

## Should fix

### 13. A `max_chars` request was not the bound it said it was
`src/tools.ts:244` (before `77c0058`)

- **What this is:** `subagent_output` returns a slice of a job's log, and `max_chars` says how big that slice may be.
- **Problem:** The bound had a floor of 200, so a request for three characters returned two hundred. The caller asked for a bound and got a different one.
- **Fix:** The request is honored as given. **Fixed in `77c0058`.**

### 14. The documented switch for background tasks did nothing in fork mode
`src/plan.ts:316` (before `cfe6348`)

- **What this is:** `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` is documented as "force every run into the foreground".
- **Problem:** Fork mode is on by default for a human in a terminal, and it removes `run_in_background` from the tool schema. The switch was checked *after* fork mode, so it did nothing for exactly the users most likely to set it: the run went to the background with no way to ask otherwise.
- **Fix:** The switch now wins. **Fixed in `cfe6348`.**

### 15. A dismissed approval left the worker waiting
`src/permission.ts:82` (before `cfe6348`)

- **What this is:** When a worker needs permission, it writes a question file and waits for an answer file.
- **Problem:** If the human dismissed the dialog, no answer was written, so the worker waited out its own permission timeout — 30 seconds in the background, minutes in the foreground — and then reported "waiting for input" as if nobody had answered.
- **Fix:** A dismissed dialog is a denial, and the refusal is written either way. **Fixed in `cfe6348`.**

### 16. Git calls block the whole session for up to 30 seconds
`src/worktree.ts:32`

- **What this is:** Every git command goes through one seam that runs `git` as a blocking subprocess.
- **Problem:** The seam allows 30 seconds, and a blocking call stops everything else in the session — the drain, the status line, the UI. A git command that waits on a lock in a big repository makes the whole mod look frozen. The hourly retention sweep can make five git calls per worktree in a row, so a spool with several worktrees can block for minutes.
- **Fix:** Lower the seam's timeout to something a user will wait for (2 seconds is what the other subprocess calls use), and make the sweep stop after one slow call rather than trying the next. The work that matters — "is this checkout worth keeping" — is a question, and a slow answer is a "keep it".

### 17. The worktree list is never pruned
`src/worktree-lifecycle.ts:290`

- **What this is:** The folder that holds the temporary checkouts.
- **Problem:** The folder grows one entry per isolated run. The sweep removes a checkout only when git says it is clean *and* the record is old enough, so a run that changed files leaves a checkout behind forever. There is no cap on how many can pile up, and nothing tells the user they are there.
- **Fix:** Report the kept checkouts in `/tasks` or `/doctor` with their paths, so the user can delete them. A cap would delete someone's work.

## Nice to have

### 18. A job id is matched as a substring
`src/index.ts:3179`

- **What this is:** A check for "does this job already have a result waiting?"
- **Problem:** The check looks for the job id anywhere in a file name. Today every id is the same length, so a wrong id cannot match — but the length grows in about fifty years, when the timestamp part gains a digit. Then one id becomes a prefix of another and the check says "yes" for a job with no result, and that job is never marked lost.
- **Fix:** Match the id as a whole field, not a substring.

### 19. The log's first page and the count of waiting signals do the same work twice
`src/delivery.ts:362`

- **What this is:** The status line shows how many results are waiting.
- **Problem:** The count re-claims and re-reads signals that the drain is about to look at anyway, once a second, forever. It is now bounded (finding 1), but it is still a second pass over the same folder every second.
- **Fix:** Have the drain keep the count as it goes and let the status line read it.

### 9. The combined no-pid-plus-error case was untested
`src/spawn.ts:281`

- **What this is:** The spawn failure paths. A worker handle with no process id
  fails the job on the spot; the handle's later `error` event fails it again.
- **Problem:** The defect itself was fixed in `eaa91f3` — a terminal job cannot
  move, so the second failure is rejected — but the two failure paths were only
  ever exercised *separately*. The case that produces the pair (one child, no
  pid, then its `error` event) was never driven, so nothing proved the two
  together produce one signal.
- **Fix:** The failure-mode table now has the combined case, and every mode
  asserts the reason the FIRST failure saved. With the state table broken, the
  combined case writes two signals and overwrites the reason with the second
  failure's — both assertions fail.

### 11. The resume test could not tell a resume from a fresh conversation
`test/e2e.mjs:294`

- **What this is:** The end-to-end suite resumes a finished agent job and asks
  it a question.
- **Problem:** The first run is given a code and the resume asks for it back. The
  code was in the FIRST prompt, so a resume that silently started a fresh
  conversation — one that echoed the prompt back — would still pass. The test
  could not tell a real resume from a restarted session, and it covered only ONE
  hop, so a chain that broke after the first resume was never exercised.
- **Fix:** The first run is given two codes. The first resume asks for one; the
  second resume resumes the *resumed* job and asks for the other, which was in no
  prompt after the first run's. The chain asserts the session name changes with
  every hop and that the whole chain continued one ACP session. With the second
  hop's session not resumed, the second resume fails and the assertions fire.

### 11a. The code question was ambiguous
`test/e2e.mjs:243`

- **What this is:** The follow-up to finding 11. Two codes, one asked for by
  name.
- **Problem:** The codes were given unlabelled, and the question — "the secret
  code" — named neither of them. A correctly resumed agent can answer with
  either code, or with both, and the history survived in every one of those
  cases. The test would still fail, and the failure would say nothing about the
  thing under test. This is not theoretical: the recorded run answered
  `zephyr-4417 quartz-8823` to the unlabelled question.
- **Fix:** The codes are labelled in the first prompt (`ALPHA is zephyr-4417`,
  `BRAVO is quartz-8823`) and each resume asks for one BY ITS LABEL, so exactly
  one code answers it. Each resume now also asserts that its answer does NOT
  contain the other code: answering with both is a correct recall of the wrong
  thing, and it would leave the second resume nothing that only the first run
  knew. With the ambiguous question restored, the first resume answers
  `zephyr-4417, quartz-8823` and the assertion fires.

## Verdict

**Healthy after this round.** Twelve real defects, all found and fixed with a test that was red before it was green. The remaining two open findings (16 and 17) are about a big repository and a long-lived spool, not about a normal run.

Two of the twelve were found by the review tool *after* this report's first pass — and one of those two was a regression introduced by the fix for the other. That is worth stating plainly: the review caught my own bug one commit after I wrote it, and the test that was supposed to catch it did not, because it asserted on the wrong thing. The lesson is the one the fix records: a duplicate must be discarded, not accepted, because accepting records the id before the result exists.

**Lean: -0 lines, -0 dependencies possible.** The split into `src/` modules is already done and each module earns its place. The deprecated `pubsub_*` names are a documented decision — "registered for one release" — not dead weight. There is no unused code to delete: every exported symbol has a caller.

**Not checked:** The `docs/wiki/` pages and `docs/adr/` were read for context but not audited for accuracy. The `WORKER_SOURCE` string inside `src/index.ts` was read where it decided a finding, but the whole embedded worker was not read line by line. The `commandcode` host itself is not in this repo, so what the host actually does with `sendUserMessage`, `ui.select` and the ACP methods was taken from the documentation and the recorded behaviour, not verified. No real-host test was run for: a background run that asks for permission (needs a human at the keyboard), a teammate, a fork, or the worktree isolation in a repository with a dirty working tree.
